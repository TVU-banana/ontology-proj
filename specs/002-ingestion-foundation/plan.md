## 3. 模块职责与依赖

| 模块 | 负责什么 | 本轮需要理解的边界 |
|---|---|---|
| domain | 业务对象、身份/单位/证据规则、校验与记录生成 | 接收普通数据，返回记录与诊断；不读取文件、环境变量或调用外部服务 |
| application | 上传登记、请求处理、管线协调、状态与结果读取 | 决定顺序，调用端口；不包含 Docling 内部对象或 Cypher |
| application/ports | FileStore、DocumentParser、FactExtractor、GraphRepository、QualityGate | 声明用例需要的能力；返回普通 DTO，不泄漏 SDK 类型 |
| adapters | 本地文件、Docling、中转模型、Neo4j 的实现 | 封装工具格式、外部 I/O 和错误；只按固定映射写图 |
| interfaces/http | 请求解析、响应序列化、错误映射 | 调用 application，不在路由中另写抽取、校验或入库逻辑 |
| bootstrap / runner | 配置注入、对象组装、任务生命周期 | 后台串行执行；后续 Agent 工具复用相同用例，不直接调用适配器 |

端口方法沿用[根 spec §14.3](../../spec.md#143-核心端口)。本阶段只建立实际需要的类型与接口；问答、报告、嵌入端口到对应节点再落实。

## 5. 首条录入链路

### 5.1 输入和对外操作

接口沿用[根 spec §14.1](../../spec.md#141-http-接口)。上传与启动处理是两个操作，避免重复上传自动触发模型调用。

| 顺序 | 操作/用例 | 输入 | 返回或产物 |
|---|---|---|---|
| 1 | POST /api/documents；RegisterDocument | PDF 字节、meta、Idempotency-Key；actor 来自服务端配置 | 新文件 201 / 同哈希重复 200；document_id、duplicate、processing_status |
| 2 | POST /api/documents/{id}/process；RequestProcessing | document_id、Idempotency-Key | 202、operation_id；已运行则返回当前 operation，不再排队 |
| 3 | runner 执行 ProcessDocumentPipeline | 已登记的可信上下文和源文件 | 解析、候选、校验/记录、图提交；每段保存结果与阶段状态 |
| 4 | GET 文档/operation 状态；ReadDocument / ReadOperation | 相应 ID | 状态、计数、warnings、产物及失败原因 |
| 5 | GraphRepository 的受控查询 | 明确文档/桥梁 ID | 首条链路的实际记录及证据对照；完整业务查询 API 在 S3.1 接入 |

本次演示 meta 使用 kind=inspection_report、source_kind=synthetic、bridge_id=B-DEMO-001。这些是来源/身份上下文，不包含病害答案；桥梁名称、构件、病害和测量仍由 PDF 抽取。候选与可信身份/来源不一致时拒绝，不让模型覆盖。

### 5.2 用例内部的顺序和责任

| 顺序 | 工作 | 责任与输出 |
|---|---|---|
| 1 | 校验输入、算 hash、保存 PDF、登记文档 | 应用协调 FileStore/GraphRepository；不能把文件存在当成图登记成功 |
| 2 | 排队、解析并保存原生/统一结构 | runner 调用 DocumentParser；业务层只接收统一文档 |
| 3 | 受限抽取、保存原始候选 | FactExtractor 返回候选；超出预算显式失败，不静默截断或读取 golden |
| 4 | 匹配证据、校验、去重、生成记录及分流 | 纯规则产生 ValidationOutcome：记录或空值、diagnostics；程序生成 ID 与 Evidence |
| 5 | 一次图事务提交记录、来源关联及审计 | GraphRepository 固定映射；图失败回滚本次写入；模型/文件操作在回调外 |
| 6 | 完成阶段与读取结果 | application 返回真实状态；嵌入尚未实现时 index_status=not_started，不声称语义检索就绪 |

这是 **S2.3 的阶段终点**：业务图可查询，向量索引仍待 S3.2。完整录入后续会接嵌入步骤，但不能因此把“图就绪”混同“所有能力就绪”。

### 5.3 状态与失败边界

文档、operation、索引和业务接纳状态分别沿用[根 spec §11](../../spec.md#11-资料录入流程与状态机)及业务契约，不合成一个 success 布尔值。

- 候选不合格：保存响应/诊断，不发布该包业务记录；面积缺失可按契约生成 pending_review，接纳状态明确保留。默认全放行不能绕过这些检查。
- 文件保存成功但图登记失败：明确登记失败，保留诊断；不承诺文件和数据库的跨资源原子性。
- 图事务失败：本次图操作回滚，既有资料不受影响；文件侧候选及诊断仍可检查。
- 重启：已保存/已提交结果可读取，未完成任务标 interrupted；不自动恢复执行或悄悄追加模型调用。
- 重传和重试分开：同 hash 重传不重跑；失败阶段由显式 retry 发起，已有运行任务不重复启动。

| A04 | 相同字节重复上传/重复提交处理 | 同文档 ID，不新增任务、模型请求或业务对象；运行中返回已有 operation；相同幂等 key 不同 payload 返回 409 | S2.3 |
| A05 | 缺面积、无效候选、错误证据 | 缺面积观测为 pending_review 且值为 null；无效候选保留诊断、不可发布；不手工改候选来通过 | S2.2–S2.3 |
| A06 | 图写入失败、完成后重启、运行中中断 | 事务回滚；完成结果持久化；中断可见且不自动续跑；旧观测与共享对象不被覆盖 | S2.3 |

## 8. S2.1 文件、来源草稿与解析详细计划

更新：2026-10-11；用户已确认本节方案，T01–T06 已实现与验收。真实 CLI/Docling、结构/位置、失败及恢复证据见 [S2.1 验收](results/s2.1/review.md)；替身/故障注入与用户验收边界分别记录。阶段决定见 [ADR-004](../../docs/adr/ADR-004-本地解析与正式图登记分阶段.md)。本节是 §5 最终链路在 S2.1 的限定交付，不能把命令行成功计为 A02 端到端通过。

### 8.1 交付范围与保存规则

本步通过命令行调用共享应用用例，完成：显式 PDF/来源上下文输入 → 原始文件与本地来源草稿 → 实际 Docling 转换 → 统一结构 → 产物校验和持久化 → 可回查的操作结果。CLI 仅负责参数/输出，不另写管线规则；未来 HTTP 复用应用能力。

标识、source.json 字段、目录、manifest 发布顺序、同哈希上下文冲突和正式登记边界统一维护在 [spec §5.2/§8](../../spec.md#8-文件布局与原子保存)，本节不建立另一份来源 Schema。文件端口/DTO 与正式 GraphRepository 职责分开；命令行不得要求图可用或伪造图登记。/ready 中图未接入状态仍如实保留。

S2.3 才接通正式上传/处理/状态 API、串行 runner 与真实图来源登记。S2.1 没有模型候选、业务 Evidence 或数据库写入；不生成空 candidates.json/chunks.json 来假装后续能力存在。

### 8.2 Docling 迁入与统一结构

1. 解析适配器接收 FileStore 管理的源路径和注入配置，不读取固定样本路径、实验 run.json 或默认实验 .env；返回原生文档、真实转换状态及告警。
2. 将实验的结构转换改成显式输入的可测试转换器，输入原生结构、应用文档 ID、可信来源上下文与页面信息；输出遵循 [spec §6.2](../../spec.md#62-normalizeddocument) 的 normalized-0.1。原生 SDK 类型只在适配器内部，应用端口返回普通数据。
3. 按 body 固定顺序深度遍历，表格按已保存 cell 顺序展开，给保留块分配连续序号；块 ID 为 `<document_id>:block:<六位序号>`（从 1 起）。保留 source_ref、层级与表格父引用；不承诺跨不同解析版本重新转换仍有相同块 ID。
4. 保留原始 text、页码、页面尺寸/旋转、locations、字符范围、原始 bbox 与规范 bbox；坐标原点可可靠转换才标 available。无 provenance、跨页单元格定位不确定、旋转或未知坐标原点时留缺项和告警，不生成猜测位置。
5. 表格保留行列、跨度和原生表头标记。实验已知 HEADER_FLAGS_ABSENT/CAPTION_LINK_ABSENT 仍可作为显式告警；本步不推断标题/单位或业务组件归属。未知内容类型保留可读取原文/来源或报告未支持项，不静默删掉。
6. 先沿用 Docling 2.137.0 实验锁定组合、CPU/4 threads、do_ocr=false、do_table_structure=true；安装时验证 Python 3.12 与应用依赖兼容，记录实际锁定版本。配置、模型缓存路径由适配器显式处理，缺模型/转换失败明确诊断，不静默下载或改 OCR 策略。确有兼容冲突时记录证据再决定调整。
7. 原生转换失败/部分完成不能发布为已完成；有效原生结果可以保留作诊断，但没有通过检查的 normalized/manifest 不算可验收快照。新产物写 DATA_ROOT，运行时不依赖 experiments。

### 8.3 验收场景与证据

| 编号 | 检查 | 通过条件 | 证据类型 |
|---|---|---|---|
| P01 | 原件保存、重复提交、来源冲突 | 原始字节/完整哈希一致；重复不触发转换；冲突明确且不覆盖 | 应用用例测试与实际命令行结果 |
| P02 | 原件通过应用实际解析 | 原生/统一结构、manifest 一致可读，配置/版本可追溯 | 真实 Docling 转换，不使用替身 |
| P03 | 关键内容与结构保留 | 三条面积原文、否定句、未知日期说明与四张表格保留；块 ID 唯一、来源引用可解析 | 独立事实清单仅由验收程序后置读取 |
| P04 | 位置核查 | 页码有效、bbox 有限且有序/在页面内、字符切片一致；绘框对应原文 | 自动检查与两页渲染人工可核查；Agent 检视不等于用户验收 |

### 9.2 本地存储与失败边界
